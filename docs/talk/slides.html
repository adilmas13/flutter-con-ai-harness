Chat feels like a conversation, but the API has no memory. “Memory” in a chat app is the app resending every earlier message on every call; the model reads the whole transcript from scratch each time. This is the real loop from agent_loop.dart, with a few lines left out (the step-limit stop message and the trace and UI updates). Walk it top to bottom: build the request from state, send it, count the step, append the assistant’s reply to the conversation. If the reply asks for no tools, we’re done: that’s a plain-text answer. The context window is the maximum size of one request. Because history is resent every turn, a long chat eventually doesn’t fit. Long before that, answers get slower, more expensive and less focused on very long inputs. A context budget is the harness checking the size before sending and deciding what to do. The user’s rules were said only at the very start, on purpose. Likely question: windows are 1M now, why care? Cost and latency scale with input on every call, and agents with tool results fill windows fast.

LEVEL 4 · TWO WAYS TO SHRINK

Summarise or remove. Both lose something.

Summarise

A separate model call turns old turns into 50 words. The last 3 turns stay.

Keeps the gist. Loses detail.

Remove

Drop the old turns. Nothing replaces them.

Cheap. Anything said only there is gone. Here: the user’s rules, so it may pick a talk ending 18:15 and break a rule.

BEYOND PROMPTS · FLUTTERCON INDIA 2026

Two strategies, both kept deliberately simple. Summarise (compaction): a separate model call turns the old turns into a summary of at most 50 words, which replaces them; the last three turns plus the current one stay. Remove: drop the old turns, keep the same recent ones, and nothing replaces what was dropped. Old messages are never deleted: the conversation is append-only and the inspector shows them struck through. They just aren’t sent. This is the “compacting conversation” moment in your coding assistant. Likely question: is the summary trustworthy? It is another model output, so it can drop or distort facts. Important facts belong in memory, which is Level 5.

Four words people use interchangeably. Context: everything in this one request. Summary: what’s left of the past after shrinking (Level 4); it lives inside one conversation. Memory: facts deliberately saved to outlive the conversation; here the model proposes each one with a tool, the user confirms, the app stores it. Level 5 adds two tools: savePreference, which proposes a fact, and getItinerary, which reads the saved plan from app state. Before savePreference runs, the loop pauses on a memory card and the user decides. If they say no, the model gets a declined result. Why confirm each memory? LEVEL 6 · GUARDRAILS

Three controls for tools that write

Approval

Any write waits for the user to approve the exact arguments.

Least privilege

Don’t send tools the task doesn’t need. A missing tool can’t be called.

Retry

A transient failure gets one retry of the same approved call.

BEYOND PROMPTS · FLUTTERCON INDIA 2026

Once a model can write to a calendar, send email or pay, its mistakes have side effects. Three classic controls, all in code. Approval: any tool marked as writing waits for the user to approve the exact arguments. Least privilege: don’t expose tools the task doesn’t need; a tool that isn’t in the request can’t be called, whatever the model reads. Retry: real services fail; the harness retries a transient error once, with the same already-approved request, instead of letting the model improvise. Likely question: won’t approval cards annoy users? Approve writes, not reads; batch them; show plain arguments, never a JSON blob.

This is how the three controls look in a real app, not the demo’s code: the demo adds an on/off switch (config.has) only so we can compare Without and With. Least privilege: the tool list comes from the task and the user’s permissions, so a tool like exportContacts is never offered to a calendar task in the first place. Approval: decided by risk, not a switch; reads run freely, anything that changes data shows the user exactly what will happen and waits. The tool then runs with exactly the approved arguments. Retry: the harness, not the model, repeats the same approved call once on a temporary error, with an idempotency key so a repeat doesn’t create a duplicate. The diagram is the order every tool call goes through; the injected exportContacts call stops at the first box, the calendar write waits at the third. Also say: the client-side check is not the security boundary on its own. The calendar and contacts APIs must check the user’s permissions on the server too. Likely question: why retry in the harness rather than let the model retry? The model may change the arguments the user approved, give up, or claim success.

Refusing the action isn’t the same as being unaffected. Flip to With: one approval card for the events; nothing is written until you click Approve, then they are created. Our demo asks before every write. A real app needs a policy. Walk the table: reads like search and get are allowed; writes to the user’s own data, like adding to their calendar, ask first; anything external or irreversible, like sending email, exporting or paying, always asks or is denied outright; and a tool this feature doesn’t need isn’t in the tool list at all, which is least privilege from earlier. There are three decisions and the strictest wins: deny beats ask beats allow. If no rule matches, the answer is ask, never allow. Rules can look at the arguments: an email to yourself can be allowed, an email to an address that came out of a tool result is denied, which is exactly the injection we just saw. It is one check in the loop for every tool call, and the model never sees the policy; it only gets “declined”. Grants like “always allow” should expire with the session. Users can tighten the policy, but only loosen it within limits the developer or an admin sets. When you do ask, show the exact arguments in plain words and batch related writes into one card. Log every decision. Likely question: how do I decide which tools ask? Ask two things: if this ran wrongly, could we undo it? And does anything leave the user’s control? If either answer worries you, ask or deny.

COMMON MISCONCEPTIONS

Six things worth unlearning

MYTH

The model remembers the conversation.

The app resends it every turn. Turn History off and turn 1 never happened.

MYTH

Tool calling means the model runs code.

It writes JSON naming a tool. Your code decides, and runs it.

MYTH

The model stops by itself when it’s done.

Usually. A vague task can keep it looping. The stop condition lives in code.

MYTH

1M-token windows make context work unnecessary.

Every call pays for its whole input, and quality drops well before the limit.

MYTH

Saying “remember this” makes it remember.

Without a way to save, “Got it” is just a reply.

MYTH

A good system prompt stops prompt injection.

The prompt and the injected text are tokens in the same request. Only code enforces a boundary.

BEYOND PROMPTS · FLUTTERCON INDIA 2026

Six misconceptions, one or two per level. Pick two or three to say out loud if time is short: the model remembers (it doesn’t; the app resends), tool calling runs code (it writes JSON; your code runs it), and a good system prompt stops injection (only code enforces a boundary). Others if time allows: the stop condition has to be in code; big windows still cost on every call and lose focus; “remember this” does nothing without a save path.
